Every good cloud security story starts with the **Principle of Least Privilege (PoLP)**. It’s simple: every service account and user should only have the absolute minimum permissions needed to do its job.

We see this challenge pop up constantly: a developer needs to deploy an application (like App Engine) that connects to a managed database (like Cloud SQL). The quickest path often tempts us to just grant the overly generous **Editor** or **Cloud SQL Admin** role to "make it work."

> *We know better.* That quick fix is a major security vulnerability that significantly expands your blast radius. This guide will walk you through defining two custom, minimal-privilege IAM roles to secure your environment properly.
> 
> oh hey, again! this guide focuses on <mark>Google Cloud Platform (GCP)</mark>, the architectural approach, separating the *deployment* role from the *runtime* role, is essential and applicable across any major cloud provider.

The Principle of Least Privilege (PoLP) dictates that every user and service account should only have the minimum permissions necessary to perform its function. In Google Cloud, developers frequently struggle with this when deploying an application (like App Engine) that connects to a database (like Cloud SQL).

## The Problem with Overly Permissive Roles

When you grant a broad predefined role, you open the door to unintended access and privilege escalation.

| **Role** | **<mark>Why It's Too Broad</mark>** | **Sample Permissions Included** |
| --- | --- | --- |
| **Project Editor** (`roles/editor`) | Grants write access to virtually *all* services in the project (Compute Engine, Pub/Sub, Storage, etc.). A compromised account can cause massive damage. | `storage.objects.delete`, `compute.instances.delete` |
| **App Engine Admin** (`roles/appengine.appAdmin`) | Grants full control over application settings, including the ability to disable the entire application or enable SSH debugging on production instances. | `appengine.instances.enableDebug`, `appengine.applications.update` |
| **Cloud SQL Admin** (`roles/cloudsql.admin`) | Grants full administrative control over the database instance itself (resizing, restarting, deleting). Most applications only need *client* access. | `cloudsql.instances.delete`, `cloudsql.instances.restart` |

Our goal is to create two specific roles:

1. **Deployment Operator:** A user role for the developer or CI/CD pipeline to deploy new versions and manage basic App Engine instances.
    
2. **SQL Connector:** A service account role for the App Engine instance to connect to the Cloud SQL database.
    

## Season 1 - Defining the Custom Deployment Operator Role

This role is for the **user** who needs to run `gcloud app deploy` and monitor instances, <mark>but </mark> *<mark>not</mark>* <mark>be able to delete the entire application or change traffic splits.</mark>

### Ep 1: Create the Role Definition YAML

We will define a custom role named `AppEngineDeployerAndViewer` at the project level. Use the following YAML content (`appengine_deployer.yaml`) feel free to title it what you like, make sure it’s a .`yaml` file.:

```yaml
title: "App Engine Deployer and Viewer"
description: "Allows deploying new versions, listing services/versions, and basic instance management (get/list/delete)."
stage: GA
includedPermissions:
- appengine.applications.get
- appengine.instances.delete
- appengine.instances.get
- appengine.instances.list
- appengine.services.get
- appengine.services.list
- appengine.versions.create
- appengine.versions.delete
- appengine.versions.get
- appengine.versions.list
- resourcemanager.projects.get
- resourcemanager.projects.list
```

### Ep 2: Create the Custom Role

Use the `gcloud` command line to create the custom role using your YAML file. Remember to replace `[YOUR_PROJECT_ID]` with your actual project ID.

```bash
gcloud iam roles create AppEngineDeployerAndViewer \
    --project=[YOUR_PROJECT_ID] \
    --file=appengine_deployer.yaml
```

### Ep 3: Grant Auxiliary Roles for Deployment

Even with the custom role, deployment requires permissions to impersonate the App Engine Service Account and interact with Cloud Build and Cloud Storage (since deployment uses these services internally).

When granting access to your developer's identity (`user:adebayo@example.com`), grant the following roles **in addition** to your custom role:

1. **Custom Role:** `App Engine Deployer and Viewer`
    
2. **Service Account User:** `roles/iam.serviceAccountUser` (Granted on the **App Engine default service account**)
    
3. **Cloud Build Editor:** `roles/cloudbuild.builds.editor` (Project level)
    
4. **Storage Object Admin:** `roles/storage.objectAdmin` (Project level)
    

This combination grants the power to deploy and manage App Engine versions without granting unnecessary control over other services like Cloud SQL.

## Season 2: Securing the Cloud SQL Connection

This role is for the **App Engine Service Account** (usually `[YOUR_PROJECT_ID]@appspot.gserviceaccount.com`). This service account needs to connect to the database but should *never* be able to delete or modify the instance's configuration.

### The Solution: Cloud SQL Client

The Cloud SQL Client predefined role (`roles/cloudsql.client`) grants the minimum permissions needed for a client application (like App Engine) to connect to a database instance. This role allows the service account to access the required network and authentication information without granting any administrative privileges.

### Ep 1: Identify the App Engine Service Account

In the Google Cloud Console, navigate to the **IAM & Admin** page, or use the gcloud CLI to identify the default App Engine service account:

```bash
echo $(gcloud app describe --format='value(serviceAccount)')
# Output will be similar to: [YOUR_PROJECT_ID]@appspot.gserviceaccount.com
```

### Ep 2: Grant the Cloud SQL Client Role

Grant the role directly to the App Engine service account.

```bash
gcloud projects add-iam-policy-binding [YOUR_PROJECT_ID] \
    --member="serviceAccount:[PROJECT_ID]@appspot.gserviceaccount.com" \
    --role="roles/cloudsql.client"
```

## Summary of Least Privilege Configuration

By following this process, you ensure clear separation of duties:

| Principal | Purpose | Granted Roles | Scope |
| --- | --- | --- | --- |
| **Developer/CI User** | Deploying Code | Custom: `App Engine Deployer and Viewer`, `Service Account User`, `Cloud Build Editor`, `Storage Object Admin` | Project / Service Account |
| **App Engine SA** (`@appspot.gserviceaccount.com`) | Running Application & Connecting to DB | `Cloud SQL Client` | Project |
